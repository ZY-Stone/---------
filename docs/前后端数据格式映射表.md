## 二、核心问题：前端期望数据格式 vs 后端实际返回

### 问题根源

前端 Zustand Store 所有数据都在**内存**中（从 Excel 直接解析或 localStorage 恢复），完全不经过后端。后端 API 虽已开发，但返回格式与前端 Store 的数据结构**不匹配**。

### 示例差异

| 场景 | 前端 Store 期望 | 后端 API 实际返回 |
|------|----------------|-------------------|
| 宽度 KPI | `width.kpi = { avgWidth, scaleCustomers, ... }` | `{ avgWidth, regulatedCustomers, ... }` 字段名不同 |
| 覆盖率排名 | `productCoverage: Array<{product, covered, rate}>` | `{ productCoverage: Array<{product, rate, count}> }` |
| 潜力 KPI | `pot.kpi = { totalSales, productCount, ... }` | `{ totalSales, productCount, ... }` 基本匹配 |

## 五、联表查询需求

| 场景 | 涉及表 | SQL 逻辑 |
|------|--------|----------|
| 部门筛选下拉 | `departments` | `WHERE visible=1` |
| 小组筛选下拉 | `groups` | `WHERE dept_id=?` |
| 产品字典-宽度27产品 | `products` | `WHERE is_potential=0` |
| 产品字典-潜力11产品 | `products` | `WHERE is_potential=1` |
| 客户名称 → 部门查找 | `width_records` + `departments` | JOIN on dept name |
| 组名 → 部门推导 | `width_records` + `groups` + `departments` | JOIN groups.dept_id = departments.id |

## 六、待修改清单

### 🔴 必须修改（否则前端无法对接）

1. **API 返回字段名统一为 camelCase**
   - `regulated_customers` → `regulatedCustomers`
   - `cust_name` → `custName`
   - 所有 `_prev` → `Prev` 等

2. **width_records 表加 `group_name` 列** — 前端 WidthRow 有 `group` 字段

3. **API 返回格式对齐前端 Store 期望**
   - Width KPI 增加 `scaleUsers`/`scaleCustomers`/`coverage` 等前端所需字段
